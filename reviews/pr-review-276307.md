# PR Review: #276307 — [Security Solution] Add advanced setting to gate rule changes history feature

**PR:** [elastic/kibana#276307](https://github.com/elastic/kibana/pull/276307) by @maximpn

**Scale:** Substantive. The diff is small in line count (253/11) but it changes gating behavior across three layers (UI, security_solution server routes, and the platform `alerting` plugin), and introduces a cross-plugin coupling that deserves scrutiny.

---

### Summary

Adds a per-space Advanced Setting `securitySolution:enableRuleChangesHistory` on top of the existing `ruleChangesHistoryEnabled` static feature flag, so the Rule Changes History feature is only active when **both** are on. The setting is registered only when the FF is on, marked `technicalPreview: true`, and defaults to `false`. Three surfaces are gated in addition to the existing FF check:

1. Front-end feature entry points (`RuleDetailsPage`, `RuleActionsOverflow`, `rules/routes.tsx`) all AND the FF with the new setting.
2. The two security_solution server routes (`GET rules/{ruleId}/history`, `POST rules/{ruleId}/history/{changeId}/restore`) now return `403` if the setting is off.
3. **New**: the platform `alerting` plugin's `logRuleChanges` skips security-solution rules when the setting is off — reading it lazily and memoizing for the duration of one call.

The PR also decorates the History menu item and the change-history page header with a "Technical preview" beta badge.

The PR description mentions items 1 and the badges. **It does not mention items 2 or 3** — the server-route gate and the alerting-plugin gate are non-trivial additions that a reader of the description won't be expecting.

### Flow trace

**"User opens the Rule Changes History tab"** — the interesting path, because it now crosses the new gates.

1. `RuleDetailsPage` (`rule_details/index.tsx:237`) computes `isRuleChangesHistoryEnabled = ruleChangesHistoryFFEnabled && ruleChangesHistoryAdvancedSetting`. If false, the tab and history routes are omitted from navigation.
2. If enabled, user hits the "History" menu item from `RuleActionsOverflow` (`rule_actions_overflow/index.tsx:107`), which does the same AND-gating and now renders the label wrapped in `TechnicalPreviewBadge`.
3. Router in `public/rules/routes.tsx:194` produces `getRulesSubRoutes(..., { isRuleChangesHistoryEnabled })`. Same AND-gating.
4. Change-history page mounts `RuleChangesHistoryPageHeader`, which shows `rule.name` followed by a bare `<TechnicalPreviewBadge label="" />`.
5. Page calls `GET /api/detection_engine/rules/{ruleId}/history`. Route handler in `rule_history/route.ts:50` resolves `['core', 'securitySolution']`, reads `ENABLE_RULE_CHANGES_HISTORY_SETTING` from the request-scoped ui-settings client, and returns `403 "Rule changes history is disabled."` if false.
6. User clicks "Restore this version" → `POST .../history/{changeId}/restore`. Same 403 gate in `restore_rule_from_history/route.ts:55`. If allowed, the existing `restoreRuleFromHistory` code path runs, which will (on success) trigger a rule update.
7. That rule update eventually calls `alerting`'s `logRuleChanges` (via bulk_edit / update paths). For each SO whose `ruleType.solution === 'security'`, `logRuleChanges` (`log_rule_changes.ts:117-126`) now lazily reads the same setting (via a fresh `uiSettings.asScopedToClient(unsecuredSavedObjectsClient)`) and skips writing to `changeTrackingService.logBulk` when off.

Note the setting is consulted at up to **three** different points in one restore flow: UI, HTTP handler, log-changes. That's not necessarily wrong — defense in depth — but it means "on" needs to be true in all three contexts (all use request/space-scoped clients, so they should agree, but see Assumptions).

### Assumptions

- `IUiSettingsClient.get()` returns `undefined` for keys that are not registered (verified in `src/core/packages/ui-settings/server-internal/src/clients/base_ui_settings_client.ts:49–75`). This PR relies on that: when the `ruleChangesHistoryEnabled` FF is off, the setting is never registered, and `get()` returns `undefined`, which `if (!x) continue;` treats as "disabled". If core ever changes that contract to throw, security-solution rule updates in the `alerting` plugin would start throwing.
- Setting reads inside `logRuleChanges` use `unsecuredSavedObjectsClient`. This client is space-scoped via `spaceId` on the `RulesClientContext`. Assumes it is always non-null (it is, per `rules_client/types.ts:72`).
- The `securitySolution:enableRuleChangesHistory` key never changes. Because the `alerting` plugin has the key as a hardcoded string (`SECURITY_SOLUTION_ENABLE_RULE_CHANGES_HISTORY_SETTING`), renaming or deprecating the setting in `security_solution` requires a matching edit in the platform plugin, and there's no compile-time or lint-time link between them.
- ESS integration tests' `--uiSettings.overrides.foo=bar` forces the value and hides the ability to test the "setting off" path via that config. Only unit tests cover the disabled behavior.
- Serverless integration tests are still `@skipInServerless` for change_tracking / restore, so the missing `--uiSettings.overrides…` in `config/serverless/config.base.ts` isn't a live problem — but whoever un-skips them later will need to add it. Comment in `change_tracking.ts:54–56` already flags the FF but not the new setting.

### Risks

Ordered by severity.

1. **(Downgraded to nit — see activity #6.)** **Cross-plugin coupling between `alerting` (platform, shared) and `security_solution` (solution, private) via a hardcoded string.** The `alerting` plugin now has a hidden runtime dependency on a `security_solution`-owned setting. The comment in `log_rule_changes.ts` acknowledges why the string is duplicated — platform can't import from a solution plugin — but the design consequence is that `alerting` now has solution-specific behavior baked in. If a second solution (e.g. observability) later wants change-tracking, the pattern will be copy-pasted. Better long-term shape would be a contract on the rule type itself (e.g. `ruleType.shouldTrackChanges?(context)` callback) so `alerting` doesn't need to know about specific solutions or setting keys. *Novelty concern softened*: `maps` plugin already reads `securitySolution:defaultIndex` this way (`x-pack/platform/plugins/shared/maps/public/classes/layers/wizards/solution_layers/security/security_index_pattern_utils.ts:22`), and `@kbn/response-ops-detections-close-reason` hardcodes `securitySolution:detectionsCloseReasons`. The pattern isn't novel; the fix-shape suggestion (activity #2's registry, or a rule-type callback) remains valid for the long term.

2. ~~**`403` is the wrong status code for a feature-disabled response.**~~ **Withdrawn** — see activity #5. The `streams` plugin uses HTTP 403 for exactly this pattern (feature-off, UI-setting-off) via `FeatureNotEnabledError`. `403` is the established Kibana idiom. Remaining minor nit is the error body: `"Rule changes history is disabled."` doesn't tell the caller how to enable it; streams-style `"…Enable "<setting-key>" in Advanced Settings to start using it."` would be more actionable. Plain English is correct (no i18n needed on server bodies — see activity #7).

3. **Silent skip in `logRuleChanges` when setting is unregistered.** If security_solution is disabled entirely, or if the FF is off, `uiSettings.get()` returns `undefined` and every security rule update silently skips change tracking. No log line, no metric. If someone later flips `xpack.alerting.ruleChangeTracking.enabled=true` in production but the security-solution FF regresses off, ops will see zero history records for security rules and no explanation why. A one-time debug/info log the first time the check evaluates falsy would help.

4. **Regressive test hygiene: mock added in `beforeEach` in `bulk_create_rules.test.ts` inside a nested `describe`.** The added `beforeEach` in `bulk_create_rules.test.ts:1100` sits in a nested describe block; it silently masks the fact that any new test in a *sibling* describe (that hits security rules) will now need the same mock or logBulk won't be called. Not a bug, but a subtle trap for future test authors. Could argue this stubbing belongs in a shared setup helper.

5. **(Downgraded to nit — see activity #6.)** **UX: `<TechnicalPreviewBadge label="" />` next to `rule?.name` in the changes-history page title.** Because the badge component prepends the `label` to the `EuiBetaBadge`, an empty label leaves just the badge floating with an 8px left margin, visually attached to the rule name. A user glancing at it may think the *rule* is in tech preview, not the history feature. The pattern used in the overflow menu (`<TechnicalPreviewBadge label={i18nActions.RULE_CHANGES_HISTORY} />`) is clearer. *Concern softened*: same `label=""` pattern already appears in `space_rules_health_page.tsx:147` and `rule_health_page.tsx:84`. It's a de-facto convention in this plugin, not a new invention. Keep the observation but no longer a should-fix.

6. **Three-point gating drift.** The setting is checked in UI, in HTTP handlers, and in `logRuleChanges`. All use request-scoped clients, so all should see the same value for the same space — but nothing enforces that in code, and a future refactor could put them out of sync (e.g. a background/scheduled job triggering `logRuleChanges` in a system context). Worth an integration test that flips the setting and verifies all three surfaces agree.

7. **[should-fix] Duplicated `FF && useUiSetting$` pattern across three UI files.** The exact same 5-line block appears verbatim in `public/rules/routes.tsx:194-200`, `public/detection_engine/rule_details_ui/pages/rule_details/index.tsx:240-247`, and `public/detection_engine/rule_details_ui/pages/rule_details/rule_actions_overflow/index.tsx:109-115`. Extract a `useIsRuleChangesHistoryEnabled()` hook next to the constant. Benefits: (a) the AND semantic lives in one place so the retirement PR is a single hook edit instead of three call-site edits; (b) the `useUiSetting$<boolean>(KEY, false)` default is defined once, so flipping the default at GA doesn't require touching three files; (c) the intent is named. Small change with an outsized payoff at retirement time. Raised in focused-review activity #6. **Naming corollary (activity #8):** the local variable names in those blocks — `ruleChangesHistoryFFEnabled`, `ruleChangesHistoryAdvancedSetting`, `isRuleChangesHistoryEnabled` — are 4-word identifiers that also echo the enclosing render context, violating the workspace `code-style-guidelines.mdc` rules ("favor short names — one or two words", "don't echo the enclosing method/file name"). Extracting the hook collapses all three names to a single `enabled` inside the hook and one clear identifier at the call site; if the hook isn't extracted, the names should still be shortened to e.g. `ffEnabled` / `settingEnabled` / `enabled`.

8. **[nit] Server-side setting reads use two different client patterns.** Routes use `ctx.core.uiSettings.client.get<boolean>(...)` (request-scoped from HTTP context — `rule_history/route.ts:52`, `restore_rule_from_history/route.ts:57`). `logRuleChanges` uses `uiSettings.asScopedToClient(unsecuredSavedObjectsClient).get<boolean>(...)` (unsecured-SO scoped — `log_rule_changes.ts:121`). Both are correct for their contexts (the alerting path may run without a request in future refactors), but the split isn't explained in a comment. A one-liner above the alerting call — "unsecured because logRuleChanges can be invoked from contexts without a request" — would prevent a future reviewer from second-guessing the choice. Raised in focused-review activity #6.

### Open questions

- ~~Why not use the existing static FF as the sole gate during tech preview?~~ **Answered (author).** FF is Kibana-wide and requires a restart; the advanced setting is per-space and toggleable at runtime. Classic tech-preview pattern: admins turn the code path on globally, space admins opt each space in individually.
- ~~Why `403` instead of `404`/`501`?~~ **Answered (broader search).** Not invented for this PR — the `streams` plugin already uses this exact pattern deliberately: `FeatureNotEnabledError extends StatusError` maps to HTTP 403, thrown for feature-flag off, license-tier off, and (relevantly here) UI-setting off (`x-pack/platform/plugins/shared/streams/server/routes/utils/assert_significant_events_access.ts:73–78`). Kibana convention for "feature is disabled" is 403. My initial "no prior art in security_solution" observation was too narrow. Only follow-up nit is the error body (see cross-questions).
- ~~Redundant third knob?~~ **Answered (author).** Intentional and temporary — the advanced setting exists only during tech preview. At GA it goes away and gating collapses back to FF + alerting config, with security-solution effectively defaulting on. Cross-question below.
- ~~`undefined` vs explicit `false`?~~ **Answered (author).** Intentional — treated as the same "disabled" state. Fine as long as it stays documented that unregistered = disabled.
- Are there any FTR or Scout tests that exercise the "setting is off" path end-to-end? Only jest unit tests appear to cover it.
- The alerting plugin change is invisible from the PR description — has `@elastic/response-ops` (the alerting plugin owner) reviewed the pattern of platform code reading a solution-specific ui-setting key by string?

### Cross-questions (raised after author's answers)

- **Error body wording, not the code.** `403` is right (streams plugin precedent). But streams' equivalent message is action-oriented — `"Significant events is disabled. Enable "streams:significantEvents" in Advanced Settings to start using it."` — while this PR ships `"Rule changes history is disabled."` with no hint of how to enable it. Suggest matching streams' style and naming the setting key in the body.
- **Retirement plan for the advanced setting at GA.** When tech preview ends, is the setting hard-removed (users who opted in silently lose the toggle) or soft-deprecated first via `UiSettingsParams.deprecation`? A hard removal at GA is defensible for a setting that was tech-preview from day one, but worth deciding now so the removal PR isn't a surprise. See activity #4 for a concrete phased plan.

### Notes for your codebase map

- **Rule Changes History gating is three-layered**: static FF (`ruleChangesHistoryEnabled`), alerting config (`xpack.alerting.ruleChangeTracking.enabled`), and now a per-space UI setting (`securitySolution:enableRuleChangesHistory`). All three must be on for the feature to work end-to-end.
- **`logRuleChanges` in `x-pack/platform/plugins/shared/alerting/server/application/rule/methods/common_utils/log_rule_changes.ts` is now the first spot in `alerting` with solution-specific gating** — reads a security_solution ui-setting by hardcoded key. Precedent for other solutions to imitate, so worth watching.
- **`IUiSettingsClient.get()` returns `undefined` for unregistered keys** rather than throwing — confirmed in `src/core/packages/ui-settings/server-internal/src/clients/base_ui_settings_client.ts:73`. Convenient for optional-setting patterns like this, but easy to mis-handle.
- **API integration tests inject setting values via CLI overrides** (`--uiSettings.overrides.<key>=<val>` in `config/ess/config.base.ts`), which bakes the value in immutably. Can't be flipped mid-suite via the SO client.
- `TechnicalPreviewBadge` is defined in `x-pack/solutions/security/plugins/security_solution/public/common/components/technical_preview_badge/index.tsx` and expects a `label`; passing `""` renders just the beta badge with an 8px margin-left.
- Security Solution's rule history / restore routes are registered conditionally in `.../api/register_routes.ts:65` based on the same FF, so the route-level `get()` won't throw on unregistered-key — the setting is guaranteed registered whenever the routes exist.

9. **Focused review — gating.** Re-read SKILL.md's `gating` section first. Traced every gating surface end-to-end. **Findings (both nits):** (1) **UI/routes don't check the alerting-side config that actually produces the records.** Security_solution UI + routes gate on `FF && setting`, but neither surface checks `xpack.alerting.ruleChangeTracking.enabled` or `xpack.alerting.ruleChangeTracking.scope`.
