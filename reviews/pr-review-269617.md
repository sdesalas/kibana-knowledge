# PR #269617 — [Security Solution] Add MVP UI for rule changes history

**Scale:** Substantive — 44 files, ~2.8k lines of cumulative diff, 4 new UI components, new route + breadcrumb + global-header branch, new client hook, new server response field. Mostly net-new under an off-by-default flag, but it also touches a few shared things (`HeaderPage`, `DiffView`, `compute_old_values`).

**Ownership (team: `@elastic/security-detection-rule-management`):** All UI files under `public/detection_engine/rule_details_ui/**`, plus the server `get_history_for_rule.*` and `compute_old_values.*` files, are owned by the target team. Shared touchpoints fall to other owners: `header_page/index.tsx`, `helpers.tsx`, `rules/routes.tsx`, `global_header/index.tsx`, `common/constants.ts`, `breadcrumbs.ts` → `@elastic/security-solution`; `deeplinks/security/deep_links.ts` → also `@elastic/security-solution`. Squarely in scope; focus review on the shared edits because regressions there hit ~34 other pages.

## Summary

Adds an MVP UI for the Detection Rule Changes History feature, gated behind the `ruleChangesHistoryEnabled` experimental flag. When the flag is on:

- A **History** entry appears in the rule details overflow menu, navigating to a new `/rules/id/:detailName/changes-history` route.
- The new page shows a left main panel with a unified JSON diff of the selected revision and a right side **push-flyout** ("Version history") with an infinite-scroll timeline of all recorded changes for that rule. The flyout's × button navigates back to the rule's Overview tab.
- Rule details subtitle now also shows `Revision` and (for prebuilt rules) `Elastic version` badges.
- Server response gains a `tracking_started_at` field on page 1, computed via a parallel `asc`-sorted query.
- `HeaderPage` gains a `backInlined` mode plus icon-only back link variant — used so the new page can put the back link on the same row as the title.

**Description ↔ diff:** the PR description says the layout is an `EuiResizableContainer` split-panel host, but the implementation is actually a `SecuritySolutionPageWrapper` with a side-mounted `EuiFlyout type="push"` (fixed 400px wide). Not resizable, not a single split-panel container. Either the description is stale or the implementation diverged; worth aligning before merge so the PR description matches what reviewers approve.

## Flow trace

1. User on rule details page, flag enabled → clicks ⋮ overflow menu → "History" (`rule_actions_overflow/index.tsx`).
2. `navigateToApp(APP_UI_ID, { deepLinkId: SecurityPageName.rules, path: getRuleChangesHistoryUrl(rule.id) })` → URL becomes `/rules/id/{ruleId}/changes-history`.
3. `RulesContainer` (`rules/routes.tsx`) sees `isRuleChangesHistoryEnabled`, matches `/rules/id/:detailName/changes-history`, mounts `RuleChangesHistoryPage`.
4. Side effects fire in parallel: `GlobalHeader` notices `isRuleChangesHistoryPath(pathname)` → unmounts the chrome action menu; `useShowTimelineForPath` hides the timeline because the path is in `EXTRA_HIDDEN_TIMELINE_PATHS`; `getTrailingBreadcrumbs` appends a "History" crumb.
5. `RuleChangesHistoryPage` calls `useRuleWithFallback(ruleId)` to fetch the rule snapshot (for the header), builds the `HeaderPage` with `backInlined` + back-link to the Overview tab + a `subtitle` and `subtitle2`, and renders `<RuleChangesHistory header={...} />`.
6. `RuleChangesHistory` calls `useInfiniteChangeHistory({ ruleId })` → `fetchRuleChangeHistoryById` → `GET /api/.../rules/{ruleId}/history?page=1&per_page=20` (versioned `'1'`).
7. Server `getHistoryForRule` runs two `rulesClient.getHistory` queries concurrently:
   - main: newest-first, `from = (page-1)*perPage`, `size = perPage + 1` (the `+1` is the predecessor needed to compute `old_values` for the oldest item on the page).
   - oldest (page 1 only): `from=0, size=1, sort=[{ '@timestamp': asc }]` to populate `tracking_started_at`.
8. Response shape: `{ page, perPage, total, tracking_started_at?, items: [{ id, timestamp, action, user, rule, old_values }] }` — `old_values` is an RFC 7396 merge patch.
9. Client renders an `EuiFlyout type="push" pushMinBreakpoint="xs"` 400px wide as the right-hand timeline panel (using a fixed CSS position calc to sit below the global header), and the main area renders the diff panel.
10. `RuleChangesHistoryTimeline` auto-selects the first "diffable" item (action ∈ `DIFFABLE_CHANGE_ACTIONS`: update/create/install/upgrade/duplicate/import/revert), and an `IntersectionObserver` on a sentinel at the bottom triggers `fetchNextPage` when it scrolls into view.
11. On selection, `RuleChangesDiff` calls `filterAndSort(rule)` → strips `IGNORED_DIFF_FIELDS` (`rule_source`, `version`, `revision`, `updated_at/by`, `created_at/by`, `execution_summary`, `meta`) and sorts keys; if `old_values` is set it calls `reconstructBefore(after, old_values)` (RFC 7396 apply with `null` → delete) and renders `<DiffView viewType="unified">` with the new `renderGutter` prop.
12. Close (× in flyout header, or any in-app nav) → `handleClose` → back to `/rules/id/{ruleId}/<overview tab>`.

## Assumptions

- The alerting framework's `xpack.alerting.ruleChangeTracking.enabled` config is also on. Without it the storage primitive that produces history events is dormant and `items` will always be empty (the FF comment in `experimental_features.ts` says so explicitly).
- `rulesClient.getHistory` accepts an arbitrary `sort` shape (`[{ '@timestamp': { order: 'asc' } }]`). The alerting API contract for `sort` isn't shown in this PR's diff; trusting that the alerting plugin already validates it.
- `old_values` from the server is a valid RFC 7396 merge patch (keys to remove encoded as `null`, otherwise replace value) — produced by `computeOldValues` server-side and reapplied by `reconstructBefore` client-side. Both share the same `IGNORED_DIFF_FIELDS` set so they can't drift.
- The `RuleHistoryItem.rule` payload is the **full post-change snapshot** (no fields stripped server-side). The client strips bookkeeping fields itself before diffing.
- `EuiFlyout type="push"` at `pushMinBreakpoint="xs"` is acceptable for the smallest viewport: 400px of permanent push is taken from the main content area regardless of viewport width.
- `useRuleWithFallback(ruleId)` returns a usable rule object even for soft-deleted rules — the page assumes the rule exists in some form to render the header (otherwise the subtitle array is `[]`).
- `<SpyRoute pageName={SecurityPageName.rules} state={{ ruleName }} />` is enough for the breadcrumb pipeline to render the History crumb. (`getTrailingBreadcrumbs` checks `pathname.includes('/changes-history')` and reads `state.ruleName`.)
- The new `SecurityPageName.rulesChangesHistory` enum entry is **not** expected to be matched by `useNormalizedAppLinks()` — that's why the page falls back to `EXTRA_HIDDEN_TIMELINE_PATHS` and the global-header URL check. The page does *not* register an AppLink of its own.

## Risks

1. **`HeaderPage` backComponent/backOptions precedence flips silently.** The original was `backOptions && ...; !backOptions && backComponent && ...` (backOptions wins). The new code is `backComponent ?? (backOptions ? ... : null)` — now `backComponent` wins. The JSDoc on `backComponent` still says *"Used only if `backOption` is not defined"*. None of the ~34 existing `HeaderPage` callers in the diff pass both, but the behavioural contract has changed and the doc is now lying. Either revert the precedence or update the doc.
2. **`SecurityPageName.rulesChangesHistory` is dead in this PR.** It's added to the shared `@kbn/deeplinks-security` enum but never used: the page sets `<SpyRoute pageName={SecurityPageName.rules} />`, no AppLink registers it, and the "hide timeline" + "no chrome action menu" plumbing routes around it via `EXTRA_HIDDEN_TIMELINE_PATHS` and `isRuleChangesHistoryPath`. Either wire it up properly (register an AppLink with `hideTimeline: true` and drop the two workarounds) or remove the enum entry — this is a shared platform type and it's strange to leak a name nothing references.
3. **`isRuleChangesHistoryPath` duplicates `RULES_CHANGES_HISTORY_PATH` by hand.** `helpers.tsx` hardcodes `` `${RULES_PATH}/id/:id/changes-history` `` (param name `:id`) while the constant uses `:detailName`. `matchPath` doesn't care about the param name so it works today; it will silently desync if anyone renames the path fragment in one place but not the other. Import the constant.
4. **`staleTime: 0` on `useInfiniteQuery`.** Every focus/remount will revalidate every page the user has already scrolled through. For a rule with a deep history this is a real cost. If the intent is "always show fresh" then OK, otherwise a few seconds of `staleTime` (or `refetchOnWindowFocus: false`) would be safer.
5. **No client-side unit/RTL tests.** Four new components (`RuleChangesHistory`, `RuleChangesHistoryTimeline`, `ChangeHistoryItem`, `RuleChangesDiff`), one new page (`RuleChangesHistoryPage`), one new hook (`useInfiniteChangeHistory`), and the `RuleVersion`/`RuleRevision` badges all ship without unit coverage. The `changes_diff.tsx` branching (nothing-selected → loading → no-old_values → no-visible-changes → no-diff-available callout → normal diff) is the kind of state machine that breaks silently when someone tweaks one branch. Acceptable behind a flag but worth tracking as a follow-up.
6. **`EuiFlyout type="push"` used as a permanent panel.** This is non-idiomatic — `EuiFlyout` is typically a transient overlay with dismissal semantics. Here the × button doesn't close anything, it navigates the user away from the page entirely. Screen-reader users in particular may not expect that from a flyout. The PR description itself describes an `EuiResizableContainer` split layout — that would match user expectations better and would also give "resizable" for free as the description claims.
7. **`compute_old_values` array equality switch is correct but expensive.** Going from element-wise `Object.is` to `lodash.isEqual` is the right fix for arrays of objects (`threat`, etc.) showing up as bogus diffs. The cost is `O(n)` deep traversal of every nested object on every rule save — for the typical detection rule shape that's nothing, but for rules with very large `threat`/`actions` arrays it's a real walk. Probably fine, just worth knowing.
8. **Server: extra `asc`-sorted query on every page=1 request.** Concurrent, capped at `size=1`, only runs for page 1 — modest. Could be derived client-side from the trailing item once the user has paged to the end, but it's a fair trade for simpler client state. Not blocking.
9. **i18n typo in the "no diff available" callout.** `NO_DIFF_AVAILABLE_CALLOUT` reads: *"Change tracking was activated while this rule already existed. Because no prior state was captured, a before/after comparison is unavailable the complete rule state at the time of this update is shown instead."* — missing punctuation between "unavailable" and "the complete". Will land in translations as-is.
10. **`subTitle` array in `RuleChangesHistoryPage` (and `RuleDetailsPage`) builds React elements without `key` props.** Minor — React will warn in dev. Same pattern existed before for `<CreatedBy>` / `<UpdatedBy>`, but the PR adds two more elements (`<RuleVersion>`, `<RuleRevision>`) and a `.filter(Boolean)` step, increasing the surface.
11. **`change_history_timeline.tsx` mixes `style={{ ... }}` with the rest of the file using `css={...}` + EUI theme tokens.** AGENTS.md says to follow file conventions; inline styles for layout-critical bits (flex, overflow, paddings) here is inconsistent with the surrounding code.

## Open questions

- Why `EuiFlyout type="push"` instead of the `EuiResizableContainer` split layout the PR description promises? Was this a scope cut, a Figma-vs-code drift, or a deliberate decision? Asking because (a) the description is now misleading and (b) a real resizable split-panel is a better fit for "primary content + always-on sidebar".
- Is `SecurityPageName.rulesChangesHistory` going to be wired up in a follow-up, or should it be deleted from `@kbn/deeplinks-security` for this PR? It's currently a no-op shared-type entry.
- Was `staleTime: 0` chosen intentionally for the infinite query? It will refetch every loaded page on every focus.
- The `ruleChangesHistoryEnabled` flag gates four things: the route, the History menu entry, the `RuleVersion`/`RuleRevision` badges in the subtitle, and (server-side) the route registration. Is "ship all four together / hide all four together" the intent, or do the revision/version badges belong to a different concern that should be released independently?
- The `RuleChangesDiff` warning callout fires for `ruleUpdate`/`ruleImport`/`ruleRevert` with no `old_values`. Can that actually happen now that `compute_old_values` always produces a merge patch (possibly empty)? If it can't, the dead branch is just defensive code — fine, but worth being explicit.
- The "Version history" sidebar title and the page header label "Rule changes history" / breadcrumb "History" don't quite agree on terminology. Final UI copy decision from `@nastasha-solomon` per the issue's action items?

## Notes for your codebase map

- **Detection rule change history is alerting-framework-owned.** `rulesClient.getHistory({ module, ruleId, from, size, sort? })` is the only entry point; security passes `module: 'security'` as the filter. There is no security-specific storage layer.
- **`old_values` is an RFC 7396 merge patch.** Server-side `computeOldValues` produces it (null = "this key existed before; it's gone now"; non-null = "this is the previous value"); client-side `reconstructBefore` applies it to the current snapshot to recover the previous state. The same `IGNORED_DIFF_FIELDS` set is used on both sides to filter bookkeeping fields out of the visible diff and the "changed fields" badge counts.
- **`HeaderPage` is the canonical page header for Security solution pages** (~35 callers). Subtitles are passed as arrays of React nodes that the header arranges; new "badge" components like `RuleVersion` / `RuleRevision` are designed to slot into that array. After this PR it also supports an inline back link via `backInlined`, which is the first non-stacked back-link variant in the codebase.
- **"Hide the timeline" / "no chrome action menu" / breadcrumb-trailing-segment** are all per-route concerns that currently piggyback on either AppLink metadata (`hideTimeline: true`) or hardcoded URL string checks (`pathname.includes('/changes-history')`). The `EXTRA_HIDDEN_TIMELINE_PATHS` workaround in `use_show_timeline_for_path.ts` is the new escape hatch for routes that don't have an AppLink — symptom of a missing primitive, worth noting if more such pages get added.
- **`DiffView` (`rule_management/components/rule_details/json_diff/diff_view.tsx`)** is now the shared unified-diff component for rule JSON across both the upgrade-rule UI and the changes-history UI. This PR makes it `renderGutter`-pluggable (and fixes a `react-diff-view` empty-hunks crash). New consumers can pass a custom gutter renderer.
- **`useNormalizedAppLinks` is the visibility/discovery layer for AppLinks**, but it's not consulted for routes registered solely inside `RulesContainer` (like this one). Pages registered there need to opt-in to chrome/breadcrumb/timeline behaviour manually — there's no central registry.
