### G1 — Restore UI eligibility is the opposite of the plan `[candidate]`

**Plan:** [L420–429](https://github.com/elastic/kibana/blob/002a4b97f87a320805579df7f7c9ad14090a049c/x-pack/solutions/security/plugins/security_solution/docs/testing/test_plans/detection_response/rule_management/rule_changes_history.md#L420) — restore still available on non-diffable actions (`rule_enable` / `disable` / `snooze` / `unsnooze` / `update_api_key` / `delete`).

**Shipped:** restore popover only if **all** of:

- action is in `DIFFABLE_CHANGE_ACTIONS` (`rule_update`, `rule_create`, `rule_install`, `rule_upgrade`, `rule_duplicate`, `rule_import`, `rule_revert`, `rule_restore`)
- row is **not** the newest (`index !== 0`)
- user has `canEditRules`

`isRestorableItem` in `change_history_timeline.tsx`. Non-diffable rows are not selectable (`isActive` false). One-pager: enable/disable have no Revert.

**Why comment:** an e2e that opens restore on a disable row (or the newest row) will fail. The Gherkin is wrong, not missing.

**Suggested rewrite:** restore only on older diffable items; no popover on enable/disable/snooze/newest; no popover without write privilege.

### G2 — Author is profile display name, not login `[candidate]` *(Steven: mention profile, not just login id)*

**Plan:** [L193–202](https://github.com/elastic/kibana/blob/002a4b97f87a320805579df7f7c9ad14090a049c/x-pack/solutions/security/plugins/security_solution/docs/testing/test_plans/detection_response/rule_management/rule_changes_history.md#L193) — “attribute the change to userA's login” + `user.id` when the realm provides a profile id.

**Shipped:** `map_rule_history_item.ts` `resolveUserName`:

```
profile.user.full_name || profile.user.email || user.name
```

Profiles loaded via `userProfileService.bulkGet` in `get_history_for_rule.ts`. Profile lookup failure is swallowed (warn + fall back to stored name). UI shows `item.user?.name` (already resolved). Serverless fix: [#278353](https://github.com/elastic/kibana/pull/278353).

**Why comment:** a tester asserting login (`alice` / `elastic`) will fail on SSO / Serverless where the row shows “Alice Smith” or an email. The plan already has `user.id`; it never says to resolve or display the profile.

**Suggested rewrite:**

```
Then the newest change item should attribute the change to userA's display name
  (user profile full_name, else email, else login)
And user.id should be present when the auth realm provides a profile id
```

### G4 — Feature availability is one of three gates `[candidate]`

**Plan:** [L522–533](https://github.com/elastic/kibana/blob/002a4b97f87a320805579df7f7c9ad14090a049c/x-pack/solutions/security/plugins/security_solution/docs/testing/test_plans/detection_response/rule_management/rule_changes_history.md#L522) — only the advanced setting. Off → no capture + get-history 403. Restore 403 already commented (L532).

**Shipped gates:**

| Gate | Off behaviour |
|------|----------------|
| Experimental `ruleChangesHistoryEnabled` | Routes **not registered** (404). History menu hidden. Advanced setting itself not registered. |
| Advanced setting `securitySolution:enableRuleChangesHistory` | Capture skipped. Get/restore **403**. Menu hidden if setting false. |
| Alerting `xpack.alerting.ruleChangeTracking.enabled` | No `changeTrackingService`. Capture no-ops. `getHistory` throws `RuleChangeTrackingDisabledError`. |

UI menu: `FF && advancedSetting` (`rule_actions_overflow/index.tsx`, `routes.tsx`).

**Why comment:** testers who only toggle the advanced setting will treat FF-off as 403 (it is 404) and never cover the alerting-framework-off path. FF is default-on and [#278197](https://github.com/elastic/kibana/pull/278197) may remove it — still true for 9.5 as shipped.

### G5 — History write is non-blocking `[candidate]`

**Plan:** out of scope is “surfacing history write failures in the UI” (OT-6). No scenario that the **rule operation still succeeds**.

**Product:** PRD OT-4 / one-pager: do not fail a rule change because history could not be written.

**Shipped:** `log_rule_changes.ts` catch → `logger.warn`, no rethrow. Transform failures are debug-logged and skipped.

**Why comment:** testers may assume a failed history write fails the rule save. That is the opposite of the contract.
