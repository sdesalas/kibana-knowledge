# Plan — bulk edit: page-wide connector prefetch (`onPage`) + full-retry validation

Issue: [#273680](https://github.com/elastic/kibana/issues/273680) · Epic: [#264906](https://github.com/elastic/kibana/issues/264906)

Base path for all files: `x-pack/platform/plugins/shared/alerting/server/`.

Line numbers refer to the current working tree, which includes 7 temporary scaffolding comments and one commented-out line (see section 0). They shift by a line or two once those are removed.

## Decisions this plan builds on

1. **Page-wide hook, not per-rule.** Connectors are fetched once per page through a new optional `onPage` hook on the shared OCC loop, rather than inside the per-rule `updateFn`.
2. **Full retry on legacy frequency.** When validation fails, `attemptToMigrateLegacyFrequency` clears rule-level `notifyWhen` / `throttle` and re-runs the *whole* validation, system-action check included. Errors are not tagged by source.

Note: the per-rule vs page-wide question was never formally answered earlier (the question was cancelled). Per-rule was the earlier recommendation. Both points above are treated as decided as of 2026-11-13 17:48.

## Prerequisites (from the main #273680 plan)

This plan assumes these exist first:

- `bulkValidateActions(context, items, opts)` in `rules_client/lib/bulk_validate_actions.ts`. It runs the `validateActions` checks and the `validateAndAuthorizeSystemActions` checks in memory.
  - `opts.connectors?: Map<string, ActionResult | InMemoryConnector>` is a prefetched connector map.
  - `opts.connectorTypes?: ConnectorType[]` is a prefetched `listTypes({ includeSystemActionTypes: true })` result.
  - `opts.skipSystemActions?: boolean` exists for the SIEM legacy path only. This plan never sets it.
  - It returns per-item errors. Single-item callers throw `errors[0]` to keep today's throw semantics.
- `extractReferences(..., { connectors? })` → `denormalizeActions(actionsClient, actions, connectors?)`.
- **Fill-in rule:** any consumer handed a map must fetch IDs that are *missing* from it, never silently drop them. This avoids the `sliceActionsById` trap from prior art [`d0483a2`](https://github.com/elastic/kibana/commit/d0483a20df2fa7e96cb7ecff036656185b69147f).

## 1. Why: what happens today

### The call chain

`updateFn` starts in the application layer, goes down into the shared OCC loop, and execution comes back up into the application file for the op logic:

1. `rules_client/rules_client.ts:235` calls `bulkEditRules(this.context, options)`.
2. In `application/rule/methods/bulk_edit/bulk_edit_rules.ts`, `bulkEditRules` (line 52) defines `updateFn` inline (line 76) and passes it to `bulkEditRulesHelper` (line 60).
3. In `rules_client/common/bulk_edit/bulk_edit_rules.ts`, the helper builds the OCC options object and forwards `updateFn: options.updateFn` (line 113) into `bulkEditRulesOcc`, inside the `retryIfBulkEditConflicts` callback (lines 104–121).
4. In `rules_client/common/bulk_edit/bulk_edit_rules_occ.ts`, `bulkEditRulesOcc` pages through rules (`perPage: 100`, line 67). For each page (loop at line 81) it:
   - runs `bulkMigrateLegacyActions` (line 91), which rewrites `rule.attributes.actions` and `rule.references` in place (`siem_legacy_actions/migrate_legacy_actions.ts:99–100`);
   - fans out with `pMap(..., { concurrency: API_KEY_GENERATE_CONCURRENCY })` (line 100; the constant is 50);
   - calls `options.updateFn(...)` once per rule (line 103).
5. Back in `application/.../bulk_edit_rules.ts`, `updateRuleAttributesAndParamsInMemory` (line 128) runs `ensureAuthorizationForBulkUpdate`, then `updateRuleInMemory` with an `updateAttributesFn` callback (line 164).
6. In `rules_client/common/bulk_edit/update_rule_in_memory.ts`, `updateRuleInMemory` (line 67):
   - resolves existing actions via `injectReferencesIntoActions` (line 95);
   - calls `updateAttributesFn` (line 123);
   - later calls `extractReferences` on the post-op action list (line 171).
7. `updateAttributesFn` calls `getUpdatedAttributesFromOperations` (`application/.../bulk_edit_rules.ts:165`). For an `actions` op, that runs `validateAndAuthorizeSystemActions` (line 286) and `validateActions` (line 296), with the legacy retry in the `catch` (lines 301–309).

### Where the redundant fetches are

Per rule, for an `actions` op, today's chain makes:

| Step | `getBulk` (ES `_mget`) | `listTypes` |
|---|---|---|
| `validateAndAuthorizeSystemActions` | 1 (op's system-action IDs) | 1 |
| `validateActions` | 1 (op's action IDs) | 1 |
| `attemptToMigrateLegacyFrequency` → `validateActions` (legacy rules only) | +1 | +1 |
| `extractReferences` → `denormalizeActions` | 1 (post-op action IDs) | — |

For **non-actions** ops (tags, schedule, snooze, `apiKey`, …), the validators don't run, but `extractReferences` still does `getBulk` once per non-skipped rule.

For 1000 rules with an `actions` op, that's about 3000 `getBulk` calls (10 pages × 100 rules × 3). Each rule in a page asks for mostly the same connector IDs: the op's IDs are identical across rules, and existing connectors are usually shared.

### Why the loop can't just fetch connectors itself

`bulkEditRulesOcc` is shared code. It's also used by `bulkEditRuleParams` (`application/rule/methods/bulk_edit_params/bulk_edit_rule_params.ts:50`), which never touches actions. The loop doesn't know what an op means, which connector IDs it needs, or whether it needs any at all. Only the bulk-edit caller knows.

That caller only ever sees one rule at a time, through `updateFn`.

### Why the hook has to sit before the fan-out

Inside `pMap` (line 100), up to 50 rules run concurrently. A fetch there happens once per rule, which is exactly today's cost. The only spot in the loop that runs once per page *and* sees the page's final pre-op actions is:

- **after** `bulkMigrateLegacyActions` (line 91), because before that, legacy SIEM sidecar actions aren't merged into `rule.attributes.actions` yet;
- **before** `pMap` (line 100), because that's where per-rule work starts.

That's lines 97–99 today, where the scaffolding comment sits.

## 2. The `onPage` hook

### Signature

In `BulkEditOccOptions` (`bulk_edit_rules_occ.ts`), next to `updateFn`:

```ts
onPage?: (rules: Array<SavedObjectsFindResult<RawRule>>) => Promise<void>;
```

The same optional field goes in `BulkEditOptions` (`rules_client/common/bulk_edit/bulk_edit_rules.ts:41–54`).

### When it's called

Once per page, inside the `for await` loop:

```ts
const migratedIds = await bulkMigrateLegacyActions({ context, rules: response.saved_objects });
migratedIds.forEach((id) => migratedRuleIds.add(id));

await options.onPage?.(response.saved_objects);

await pMap(response.saved_objects, async (rule) => options.updateFn({ ... }), { concurrency: API_KEY_GENERATE_CONCURRENCY });
```

- It's awaited. No `updateFn` for that page starts until `onPage` resolves.
- It runs again on every retry attempt. `retryIfBulkEditConflicts` re-invokes `bulkEditRulesOcc` with an ID filter for the 409'd rules, so the retry gets fresh pages and a fresh `onPage`.
- It isn't called for empty pages, because the finder doesn't yield them.

### What it receives

The raw page: `response.saved_objects`, as decrypted `SavedObjectsFindResult<RawRule>`. Legacy migration has already been applied. Each item has `attributes.actions` (with `actionRef`) and `references`, and that's enough to resolve existing connector IDs with `injectReferencesIntoActions`.

It gets nothing else: no op, no context. The caller's closure already has those.

### How it differs from `updateFn`

| | `onPage` | `updateFn` |
|---|---|---|
| Cardinality | Once per page (≤100 rules) | Once per rule |
| Concurrency | Sequential, awaited before the fan-out | Up to 50 in parallel |
| Job | Read-only prep: fetch shared data for the page | Compute the edited rule, push into `rules` / `skipped` / `errors` |
| Writes to the loop's accumulators | No | Yes |
| Required | No (optional) | Yes |
| Error contract | Must not throw (soft-fails internally; see section 3) | Catches its own errors into `errors` (`application/.../bulk_edit_rules.ts:183–197`) |

### Contract for the shared loop

The loop treats `onPage` as opaque: it calls it and awaits it, nothing more. If `onPage` throws anyway, the error propagates out of `bulkEditRulesOcc` and fails the whole bulk call. That's why the soft-fail lives in the caller's implementation, not the loop.

### Getting the data to `updateFn`

**Chosen: closure state in the caller.** `bulkEditRules` creates a page-scoped holder that both `onPage` and `updateFn` close over. `onPage` replaces it each page, and `updateFn` reads it. This leaves `UpdateOperationOpts` and the shared loop's types untouched.

It's safe because pages are strictly sequential: the `for await` loop awaits each page's `pMap` before reading the next page. Within a page, `updateFn` calls only read the holder.

The alternative (open question 1) is for `onPage` to return a value that the loop passes into each `updateFn` call as an opaque field.

## 3. Fetch once per page, use the map per rule

### The page holder

In `bulkEditRules` (`application/.../bulk_edit_rules.ts`):

```ts
let page: { connectors?: Map<string, ActionResult | InMemoryConnector>; connectorTypes?: ConnectorType[] } = {};
```

An empty holder means "no prefetch", and consumers fall back to fetching for themselves.

### `onPage`, step by step

1. **Collect op IDs.** From `options.operations`, take every op with `field === 'actions'` and collect `value[].id`. That covers both default actions and system actions, since the op value holds both. These are the same for every rule, so they could be computed once outside `onPage` and reused.
2. **Collect existing IDs.** For each rule in the page, run `injectReferencesIntoActions(rule.id, rule.attributes.actions ?? [], rule.references ?? [])` and collect `id`s. This is the same resolution `updateRuleInMemory` does at `update_rule_in_memory.ts:95`, so the IDs match what extract later sees. It covers:
   - the existing actions that `add` keeps;
   - what's left after `delete`;
   - the full set for non-actions ops.
3. **Union and dedupe** into a `Set<string>`. The page's union is typically O(10) IDs, against O(100) rules.
4. **Fetch once:** `actionsClient.getBulk({ ids, throwIfSystemAction: false })`. In-memory (preconfigured and system) connectors are resolved without ES, and saved-object connectors take one `_mget`.
5. **Types once:** `actionsClient.listTypes({ includeSystemActionTypes: true })`. `validateActions` uses `listTypes({})` and the system validator uses the `includeSystemActionTypes: true` superset. Either the full list is shared, or `bulkValidateActions` filters system types out where `validateActions` didn't see them (see risk R6). Types don't change per page, so this can be fetched once per bulk call and reused across pages.
6. **Store by ID:** `page = { connectors: new Map(results.map((c) => [c.id, c])), connectorTypes }`.
7. **Skip when there's nothing to fetch.** If the union is empty, set `page = {}` and return.
8. **Soft-fail.** Wrap steps 4–5 in `try/catch`. On error, log at `debug`/`warn`, set `page = {}`, and return. The rules on that page then behave exactly as today, with per-rule fetches and per-rule error attribution (see risk R1).

### `updateFn` and the consumers, per rule

`updateFn` (line 76) already closes over `bulkEditRules`' scope. It reads `page` and threads it down:

1. `updateRuleAttributesAndParamsInMemory({ ..., page })`.
2. Inside it:
   - `getUpdatedAttributesFromOperations({ ..., page })` gets the map for validation;
   - `updateRuleInMemory(context, { ..., connectors: page.connectors })` gets it for extract.
3. **Validation** (`getUpdatedAttributesFromOperations`, `actions` case): the two separate calls become one:

   ```ts
   try {
     await bulkValidateActionsOne(context, ruleType, {
       data: { ...updatedRule, actions: genActions, systemActions: genSystemActions },
       rule: { consumer: updatedRule.consumer, producer: ruleType.producer },
     }, { connectors: page.connectors, connectorTypes: page.connectorTypes });
   } catch (e) {
     updatedRule = await attemptToMigrateLegacyFrequency(context, operation.field, genActions, genSystemActions, updatedRule, ruleType, page);
   }
   ```

   `bulkValidateActionsOne` stands for "call `bulkValidateActions` with one item and throw `errors[0]`". Whether that's a tiny helper or inline is an implementation detail.
4. **Extract** (`update_rule_in_memory.ts:171`): `extractReferences(context, ruleType, updatedRuleActions, params, artifacts, { connectors })`. This is the post-op list, so for `add` / `delete` it includes existing connectors, and those are in the map because of step 2 above.
5. **Fill-in for missing IDs.** Both `bulkValidateActions` and `denormalizeActions` check each needed ID against the map and do one `getBulk` for any that are missing. That happens if:
   - `onPage` soft-failed (empty map, so everything is fetched, as today);
   - something added an ID after `onPage` ran. Nothing does today, but this keeps it correct if `paramsModifier` or a future op ever does.

### Resulting fetch count

| Scenario (1000 rules, 10 pages) | `getBulk` today | `getBulk` after |
|---|---|---|
| `actions` op (`set` / `add` / `delete`) | ~3000 | 10 |
| Non-actions op | ~1000 | 10 |
| `onPage` soft-fails on one page | — | 1 + that page's per-rule fetches (as today) |
| `bulkEditRuleParams` | unchanged | unchanged |

## 4. Legacy frequency migration and full-retry validation

### Background

Before per-action frequency (8.7, [#145637](https://github.com/elastic/kibana/pull/145637), 2023-01), rules carried rule-level `notifyWhen` / `throttle`. `validateActions` rejects mixing the two shapes:

- rule-level frequency set **and** any action has `frequency` → "Cannot specify per-action frequency params when notify_when or throttle are defined at the rule level";
- rule-level frequency **not** set **and** any action lacks `frequency` → "Actions missing frequency parameters".

So when you bulk-edit a legacy rule and add per-action-frequency actions, the first validation fails. `attemptToMigrateLegacyFrequency` (`application/.../bulk_edit_rules.ts:462`) handles that by clearing the rule-level fields and validating again. The rule is migrated to per-action frequency as a side effect of the edit. Git history: introduced in [`ff6024d`](https://github.com/elastic/kibana/commit/ff6024defc96), logic unchanged since. The public API still accepts rule-level `notify_when` / `throttle`, so the legacy shape is still reachable.

### Today's ordering, and why it matters

```ts
await validateAndAuthorizeSystemActions({ ... });   // A: outside the try; failure throws straight out
try {
  await validateActions(...);                         // B
} catch (e) {
  updatedRule = await attemptToMigrateLegacyFrequency(...);  // re-runs B only
}
```

Because A sits outside the `try`, a system-action failure (bad system action, duplicate, missing privilege) can never be swallowed by the retry.

### New behavior

Once A and B become one `bulkValidateActions` call inside the `try`, the `catch` can't tell which check failed. The chosen answer is that **the retry re-runs everything**:

1. First attempt: full `bulkValidateActions` (A + B) against `page.connectors` / `page.connectorTypes`.
2. On any error, `attemptToMigrateLegacyFrequency`:
   - throws if `operation.field !== 'actions'` (unchanged);
   - clears `updatedRule.notifyWhen` if defined and `updatedRule.throttle` if truthy (unchanged, mutates `updatedRule`);
   - calls full `bulkValidateActions` again with the same `genActions` / `genSystemActions` and the same `page` map. There is **no** `skipSystemActions`.
3. Outcomes:
   - **The failure was legacy frequency.** The retry passes and the rule is migrated. It costs one extra system-action auth check (`actionsAuthorization.ensureAuthorized`), and only when the op includes system actions. There's no extra connector fetch, because the map is reused.
   - **The failure was a system-action error.** The retry fails with the same error, which propagates and is caught into `errors` by `updateRuleAttributesAndParamsInMemory`. Nothing is swallowed.
   - **The failure was some other actions error** (bad group, invalid throttle, alertsFilter …). The retry fails with that error, as today.
   - **Both legacy frequency and a system-action error.** The retry clears frequency, the actions checks pass, the system check fails, and the system error is surfaced. That's correct.

### Why not tag errors by source

Tagging (for example, a result `{ actionsError?, systemActionsError? }`) would let the retry skip A. But it adds an error-shape contract that every caller of `bulkValidateActions` would have to understand, all to save one auth check on a rare path. Not worth it.

### Small behavior alignments in the retry

- Today the retry passes `{ ...rule, actions }`. That leaves `systemActions` coming from the *existing* domain rule (`rule.systemActions`), which `validateActions` only uses for the duplicate-UUID check. The new retry passes `systemActions: genSystemActions`, the same as the first attempt. That's consistent, and it's needed now that system checks run in the retry. Flagged as a minor behavior change (risk R5).
- `attemptToMigrateLegacyFrequency`'s signature gains `genSystemActions` and `page`.

### Where `skipSystemActions` is still used

Only in `rules_client/lib/siem_legacy_actions/transform_and_delete_legacy_actions.ts` (`validateTransformedActions`), which is outside this plan.

## 5. Wiring: `bulkEditRules` sets `onPage`, `bulkEditRuleParams` leaves it unset

- **`bulkEditRules`** (`application/rule/methods/bulk_edit/bulk_edit_rules.ts`) passes both `updateFn` and `onPage` to `bulkEditRulesHelper`. Both close over the same `page` holder and the same `options.operations`.
- **`bulkEditRuleParams`** (`application/rule/methods/bulk_edit_params/bulk_edit_rule_params.ts:50`) doesn't change at all. It never sets `onPage`, so `options.onPage?.(...)` is a no-op and its `updateFn` path (`updateRuleInMemory` → `extractReferences` without a map) fetches as today.
- **The shared helper** (`rules_client/common/bulk_edit/bulk_edit_rules.ts`) just forwards the field. It knows nothing about connectors.

A later PR could opt `bulkEditRuleParams` into a page prefetch for its `extractReferences` leg. That's out of scope here.
